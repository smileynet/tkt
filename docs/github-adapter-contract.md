# GitHub issues adapter v1 — design contract

This is the first external-system adapter design for ticket 125, not a shipped import command or generic mapping engine. Its concrete use case is the existing GitHub-import request in ticket 86. That is recorded product intent; there is no independently observed customer migration corpus. GitHub is selected on that basis, not merely because tkt is hosted there. `tkt migrate --help` currently advertises only `tk`; no `--map`, `migrate.toml` executor or GitHub importer exists.

## Provider and extraction boundary

Contract identifier: `github-issues/v1`. Source: GitHub REST repository issue objects using explicit API version `2026-03-10`, the version shown by the current primary documentation. Initial supported host is github.com; Enterprise hosts require a separately verified API-version/auth contract. Credentials stay in `gh`; tkt must never read/log tokens or save authentication headers.

Use authenticated read-only `gh api` requests for repository metadata and paginated repository issues with explicit `state=all`, with explicit repository/host and API-version headers. The REST issues endpoint includes pull requests, distinguished by `pull_request`; filter them out. Request raw Markdown, not rendered HTML. Pagination must be complete before allocating or writing tickets. Pagination is a bounded observation, not a transactional provider snapshot. Deduplicate identical repeated issue IDs across pages; if the same ID has different state/content/provenance during one extraction, abort planning without writes. Recheck local identities and conflicts on every allocation retry, but do not claim source freshness after extraction. Source facts and version: [GitHub repository issues REST reference](https://docs.github.com/en/rest/issues/issues#list-repository-issues). The installed `gh` is 2.89.0; `gh api --help` confirms authenticated requests, explicit headers and pagination. [GitHub CLI api manual](https://cli.github.com/manual/gh_api) owns invocation details. `gh issue list` has a result limit, so its default listing is not a completeness guarantee; [list manual](https://cli.github.com/manual/gh_issue_list).

First release imports open issues only; extraction requests state=all so closed/PR skip counts describe received objects, not an inferred total. The issue bound applies to all received objects, including skipped ones. Closed objects are explicitly skipped with counts, never fabricated as tkt done. Unknown states, missing required identity/title/URL, mixed repository identities or malformed pages fail planning without writes. Maximums must be declared in help and preview; reaching any bound is an incomplete-input error, never silent truncation. Proposed initial bounds: 1,000 issues and 10 MiB total raw JSON, measured before expansion; larger migrations need an explicit future mode. Network/auth/rate-limit/page failure produces no local import commit. A dry-run may read the provider but makes no local persistent effects.

## Identity and mapping

Canonical source identity is `(github.com, issue.id)` with repository numeric ID, owner/name, issue number and canonical `html_url` recorded as provenance. Require a positive numeric issue ID and repository metadata matching the requested repository. Do not use `github#NN` or issue number alone. In fixture v1 identity is local to the verified GitHub host; repository rename may update display provenance without allocating another local ID when the same issue ID is observed. Transfers, deleted/recreated issues and provider ID semantics across hosts are outside supported first-import behavior; mismatched provenance requires explicit conflict review rather than guessing identity.

| Source | Local result |
|---|---|
| Open issue with title/body | New local open ticket, normal local ID allocation, quoted scalar title, generated import slug; never reuse provider number as local ID. |
| `id`, URL, repository and number | Raw scalar `import_source` identity plus full provenance in owned JSON snapshot. Unknown frontmatter round-trips under existing raw preservation; no new typed field contract is implied. |
| Body Markdown | A null body renders as an empty source section, while JSON null remains null in the snapshot. Keep exact source body in snapshot; rendered local body gets an import provenance section and explicit source-body section. Local acceptance/validation criteria are not inferred from GitHub task checkboxes. |
| Labels | Preserve complete original list in snapshot; no automatic priority, eligibility, capability or closed-namespace tags. Add only a fixed documented import stream tag; any configured closed-label conflict fails preflight. |
| Closed / pull request | Skip with separate reason/count. |
| Milestone, assignees, project fields, relationships | Preserve raw values; no automatic parent, dependency, local assignee or lifecycle mapping. |
| Unknown keys or enum values in otherwise accepted object | Preserve complete raw object. Reject only unknown values that affect supported required semantics, such as state. |

The source-body section uses a fenced block with a delimiter longer than any matching source fence, so unqualified source `#NN` and task checkboxes cannot become local citations/acceptance criteria. The snapshot preserves bytes as supplied by the JSON decoder (original provider JSON wire formatting is not claimed). The import summary links the canonical issue URL outside the fence. This is a deliberate presentation tradeoff: raw source Markdown remains readable, but does not pretend to be native tkt acceptance or local relations. A later explicit conversion can promote selected work into local criteria.

## Preservation, ownership and replay

Store snapshots at `.tickets/imports/github-v1/<issue-id>.json`, using only validated numeric IDs and including the host in the receipt. This directory is owned per imported identity, not by its name alone. The ticket's `import_source` value is `github.com:issue:<id>`; the snapshot contains format, source identity, local ID, canonical issue URL, complete source object, extraction API version and hashes of generated ticket bytes. It is not an executable map file. `load_corpus` must continue scanning ticket Markdown only; verify nested JSON cannot be misread as tickets.

Import is create-only in v1. Same source identity already recorded with valid matching ownership is a skipped existing ticket, even if the provider body/state has changed; report that update synchronization is unsupported. Never overwrite local notes, criteria, lifecycle or evidence. Duplicate identity across multiple local tickets, a missing referenced ticket, modified ownership metadata, unmanaged snapshot collision or mismatched repository provenance is a conflict. Report all conflicts before writing. Empty successful replay is a no-op without commit/push.

Plan fetch results separately from local application. Reuse the allocation transaction's fresh scan/ID collision retry and push policy; refresh identity deduplication on each retry. Write ticket and snapshot with atomic writes on the same filesystem, record an operation journal before application, and commit only the planned ticket/snapshot paths. Plan changes only through existing plan synchronization semantics; do not stage unrelated files. Journal recovery must detect an interrupted pair and complete the same identity/local ID without duplicates. Concurrent operations use the repository mutation/allocation serialization contract; if the existing transaction cannot serialize snapshot pairs, add a focused lock before shipping. Never claim that separate atomic writes make the whole batch atomic. Push failure names durable local commit/retry, preserving existing push-disabled behavior.

## Fixtures and implementation plan

[Design fixtures](evidence/github-adapter-125.json) use synthetic provider objects and expected outcomes, not real customer data or a passing importer. They cover separate repositories sharing issue numbers, same identity replay, quoted/newline text, unknown fields/state, closed/PR exclusion, missing identity, unsupported relations and unmanaged/duplicate provenance. Preserve fixture unknown fields in snapshots exactly as JSON values.

Ticket 86 implements this contract: (1) pure source decoder/mapping and identity inventory; (2) paginated read-only extraction with error/bound fixtures; (3) dry-run preview; (4) atomic owned ticket/snapshot journal and allocation retry; (5) public isolated fake-gh integration tests including interruption, concurrency, replay, push-disabled, no-write dry-run, auth/page errors and Git scope. All agent guidance surfaces need updating when the command actually ships. The proposed interface remains `tkt import --github` with an explicit repository selector and label filter; exact flags must be reconciled with Clap/global flags during implementation.

No Jira, Linear, GitLab, arbitrary TOML mapping language, general sync engine, comments/attachments download, provider writes or closed-ticket lifecycle migration is included. Existing tk migration remains separate and supported; this adapter does not claim compatibility with its implementation internals.

## Verification and remaining uncertainty

PASS: current CLI help/source establishes the absent generic map interface and existing tk-only migration; primary provider/CLI sources establish extraction constraints. Synthetic cases specify mapping requirements; they do not prove any importer works. No GitHub issues were created, edited, imported or closed. Pagination consistency during remote edits, journal recovery, snapshot ownership validation and provider-version compatibility remain implementation verification obligations in 86.
