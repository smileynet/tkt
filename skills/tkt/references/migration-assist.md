# migration-assist

Help users convert tickets from any format into tkt's schema.

## When to use

- .tickets/ contains files in a non-tkt format
- `tkt migrate` auto-detection failed or produced low-confidence results
- Importing from a system tkt doesn't have a built-in adapter for
- User wants to review or customize the mapping before applying

## Workflow

1. **Sample** — read 3-5 tickets from the source directory
2. **Analyze** — identify the schema: fields, values, ID pattern, naming
3. **Propose** — draft a `migrate.toml` with field renames, enum maps, ID strategy
4. **Preview** — show 2-3 tickets before/after so the user sees exactly what changes
5. **Confirm** — user approves or adjusts the map
6. **Apply** — `tkt migrate --map migrate.toml --apply`

## Analysis steps

### 1. Detect schema shape

Read all frontmatter keys across the corpus:

```bash
# Quick key inventory
grep -h "^[a-z_]*:" .tickets/*.md | cut -d: -f1 | sort | uniq -c | sort -rn
```

For each key:
- Count occurrences (is it universal or sparse?)
- Sample 5-10 distinct values
- Classify: direct tkt equivalent, needs value mapping, or unmapped

### 2. Identify format signals

| Signal | tkt native | tk format | GitHub-style | Custom |
|--------|-----------|-----------|-------------|--------|
| Filename | `NN-slug.md` | `slug.md` | `NNN.md` | varies |
| ID field | `id: "01"` (quoted numeric) | none or slug | `number: 42` | varies |
| Deps | `blocked_by: ["01"]` | `deps: [slug]` | none | varies |
| Status done | `done` | `closed` | `closed` | varies |
| Title | `title: "..."` | body H1 | `title: "..."` | varies |

### 3. Propose mappings

For each source field, recommend one of:
- **Rename** → direct equivalent (`deps` → `blocked_by`)
- **Map values** → enum translation (`closed` → `done`, `wip` → `in_progress`)
- **Extract** → derive from content (`title` from body H1)
- **Drop** → no tkt equivalent, inform user what's lost (`assignee`, `labels`)
- **Preserve** → keep as-is if tkt already supports it

### 4. Generate migrate.toml

```toml
# Auto-generated by migration-assist. Review before applying.
# Run: tkt migrate --map .tickets/migrate.toml --apply

[source]
format = "tk"                     # detected format
confidence = "high"               # high/medium/low

[fields]
deps = "blocked_by"               # rename key
# assignee = ""                   # DROPPED — tkt doesn't track assignees

[values.status]
closed = "done"
wip = "in_progress"
todo = "open"
# REVIEW: "blocked" found 3 times — map to "open" with blocked_by? or "backlog"?

[values.priority]
1 = "urgent"
2 = "high"
3 = "medium"
4 = "low"

[id]
strategy = "renumber"             # renumber | preserve | prefix
# Mapping: old-slug → new-id (generated on apply)

[title]
source = "body_h1"               # frontmatter | body_h1

[options]
backup_dir = ".tickets.bak"
drop_unknown_fields = true        # warn and drop fields not in [fields]
```

Mark uncertain mappings with `# REVIEW:` — the user or agent checks these before applying.

### 5. Preview (before/after)

Show 2-3 representative tickets side by side:

```
--- BEFORE: deploy-pipeline.md ---
deps: [auth-system, api-endpoints]
status: closed
priority: 1

# Deploy pipeline
...

--- AFTER: 03-deploy-pipeline.md ---
id: "03"
title: "Deploy pipeline"
status: done
blocked_by: ["01", "02"]
priority: urgent
```

Highlight:
- Data that would be lost (dropped fields)
- Uncertain mappings (# REVIEW items)
- ID remapping table

## Rules

- Never apply a migration without showing the preview first
- Always generate the map file — even for auto-detected formats (documents what happened)
- Flag fields with no tkt equivalent (inform, don't silently drop)
- If >20% of fields are unmapped, flag it — the source may not be a good fit for tkt
- The map file is the contract: what it says is what happens, nothing more
- Preserve the map file after migration (it's the audit trail of what was converted)

## Agent integration

For non-interactive use (agent builds the map):

```bash
# Agent reads samples, generates the map
tkt migrate --generate-map       # outputs migrate.toml from corpus analysis

# Agent reviews the map, then applies
tkt migrate --map migrate.toml --dry-run   # preview
tkt migrate --map migrate.toml --apply     # execute
```

The map file is the seam between judgment (proposing mappings) and execution (applying them mechanically).
